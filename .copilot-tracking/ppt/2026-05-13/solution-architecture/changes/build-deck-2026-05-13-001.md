## How the `_source-reference/` exclusion was handled

The build script's slide discovery (`discover_slides` in `build_deck.py`) iterates the
content directory non-recursively (`Path.iterdir()`) and filters to directory names
matching `^slide-(\d+)`. The `_source-reference/` folder does not match that prefix and
its nested `slide-NNN/` subfolders are at depth 2, so they are naturally invisible to
the discoverer.

No renaming, slide-list filtering, or workarounds were required. Verified empirically:
the build produced exactly 15 slides matching `content/slide-001` … `content/slide-015`.

### Note on slide width — 12,191,695 vs 12,192,000 EMU

The verification flagged `slide_width_emu == 12191695`, which is 305 EMU short of the
spec's stated 12,192,000.

Root cause: the build script invokes `prs.slide_width = Inches(width)` with `width =
style.yaml::dimensions.width_inches = 13.333`. `python-pptx.util.Inches(13.333)` is
`int(13.333 * 914400) = 12,191,695`. The exact value 12,192,000 corresponds to
PowerPoint's internal "Widescreen 16:9" preset of exactly `40/3` inches
(13.333_3̄ inches). The 305-EMU gap is ≈ 0.000334″ (≈ 8.5 µm) — below display
resolution; PowerPoint renders both as `13.333" × 7.5"` and reports identical
"On-screen Show (16:9)" page setup.

If perfect 12,192,000 EMU is required (for example, for byte-identical comparisons
against another widescreen deck), update `content/global/style.yaml` to
`width_inches: 13.333333333` (or extend `style.yaml` and `build_deck.py` to accept a
direct `width_emu`/`height_emu` override). No content or layout problem follows from
the current value; both width and height display correctly and aspect ratio is the
intended 16:9.
